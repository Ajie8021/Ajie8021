# 总计与改进计划

## 1. 项目概述

本项目实现了一个基于 Java 的小学四则运算题目生成与批改程序。

项目主要功能包括：

- 根据命令行参数生成指定数量的四则运算题目；
- 支持自然数和真分数；
- 支持整数、分数以及带分数；
- 限制表达式最多包含 3 个运算符；
- 保证减法结果不为负数；
- 保证除法结果为真分数；
- 对生成题目进行重复判断；
- 将题目输出到 `Exercises.txt`；
- 根据题目文件和答案文件进行批改；
- 将批改结果输出到 `Grade.txt`。

项目采用 Java 25 + Maven 实现，并使用 JUnit 进行模块化测试。

## 3. 实际开发过程中遇到的问题

### 3.1 需求描述存在一定歧义

项目最困难的地方并不是 Java 语法，而是如何把自然语言需求转换成可以执行的程序规则。

例如：

```tex
3 + (2 + 1)
```

和：

```tex
1 + 2 + 3
```

是否属于重复题目？

如果简单地把所有加法操作数排序，会错误地将更多结构不同的表达式判断为重复。

因此最终采用表达式树，并只对 `+` 和 `×` 的**直接左右子树进行规范化交换**。

这使程序能够保留表达式的树结构，同时处理题目要求中的有限次交换。

## 4. 分数计算问题

如果直接使用 `double` 保存分数，会存在浮点数精度问题。

例如：

```tex
1/3 + 1/3 + 1/3
```

使用浮点数可能得到：

```tex
0.999999...
```

而不是精确的：

```tex
1
```

因此项目最终使用：

```tex
BigInteger numerator
BigInteger denominator
```

实现不可变的 `Fraction` 类。

这种设计虽然代码量有所增加，但能够保证分数计算的精确性。

## 5. 表达式设计问题

最初可以考虑直接使用字符串生成题目，例如：

```tex
1 + 2 × 3
```

然后通过字符串处理判断表达式。

但随着需求增加，这种方式会产生较多问题：

- 运算符优先级处理复杂；
- 括号处理复杂；
- 表达式计算困难；
- 判断等价表达式困难；
- 题目结构难以保存。

因此项目最终使用表达式树：

```tex
        ×
       / \
      +   3
     / \
    1   2
```

对应：

```tex
(1 + 2) × 3
```

这样可以统一支持：

- 计算；
- 验证；
- 格式化；
- 解析；
- 规范化；
- 去重。

## 6. 随机生成模块的问题

随机生成题目时，一个重要问题是：

> 随机生成的表达式可能不合法，也可能与已经生成的题目重复。

因此生成过程采用：

```tex
随机生成
    ↓
合法性验证
    ↓
规范化
    ↓
Set 去重
    ↓
加入结果
```

只有通过验证并且没有重复的表达式才能最终加入题目集合。

同时增加最大尝试次数，避免在题目数量过大或者参数范围过小时出现无限循环。

## 7. 测试过程中的收获

本项目的测试没有只测试“正常情况”，还测试了大量边界情况。

例如：

```tex
0
1/2
1'1/2
3 - 5
5 - 3
1 ÷ 2
3 ÷ 2
除数为 0
超过 3 个运算符
```

通过这些测试发现，异常情况往往比正常情况更容易暴露设计问题。

因此，在后续项目中应该在设计阶段就同步考虑测试用例，而不是编码完成之后再临时补测试。

## 8. 模块化设计的效果

项目最终划分为：

```tex
cli
model
calculator
validator
normalizer
generator
parser
io
grader
exception
```

这种设计使不同功能之间具有较明确的职责边界。

例如：

```tex
Fraction
```

只负责分数表示和计算；

```tex
ExpressionCalculator
```

负责表达式计算；

```tex
ExpressionValidator
```

负责表达式合法性；

```tex
ExpressionNormalizer
```

负责表达式规范化。

因此，如果以后修改分数计算方式，不需要修改题目生成、CLI 或批改模块。

## 10. 可以改进的地方

### 10.1 随机生成策略仍然可以进一步优化

当前生成器主要采用：

```tex
随机生成 → 验证 → 去重
```

这种方式实现简单，但当参数范围较小时，随机生成大量无效表达式的概率会上升。

后续可以考虑：

- 根据运算符类型生成合法操作数；
- 生成除法时提前构造满足真分数条件的操作数；
- 生成减法时提前保证左值大于等于右值；
- 根据当前已生成题目动态调整随机策略。

这样可以减少无效生成和重复生成。

### 10.2 可以进一步完善参数提示

当前参数错误已经能够被捕获。

后续可以进一步优化帮助信息，例如：

```powershell
Usage:

Generate:
java -jar arithmetic-project.jar -n <number> -r <range>

Grade:
java -jar arithmetic-project.jar -e <exerciseFile> -a <answerFile>
```

使第一次使用程序的用户可以直接根据提示运行。

### 10.3 可以增加更完整的集成测试

目前测试主要集中在模块级单元测试。

后续可以增加：

```tex
命令行参数
    ↓
Main
    ↓
ExerciseGenerator
    ↓
FileManager
    ↓
Exercises.txt
```

以及：

```tex
Exercises.txt
    ↓
Grader
    ↓
Grade.txt
```

这样的端到端测试。

### 10.4 可以进一步量化性能

当前项目已经能够生成大量题目，但性能分析还可以更加系统。

后续可以记录：

- 生成 100、1000、5000、10000 道题所需时间；
- 不同 `-r` 参数下的生成时间；
- 重复检测所占时间；
- 表达式规范化所占时间；
- 文件写入所占时间。

通过数据判断真正的性能瓶颈，而不是仅凭主观判断。

## 11. PSP 过程改进

根据本次项目的实际开发过程，下一次项目可以进行以下改进。

### 改进一：需求分析阶段增加边界条件清单

以后进行需求分析时，在正常需求之外单独建立：

```tex
输入边界
数据边界
异常情况
性能边界
输出格式
```

例如本项目应该提前列出：

```tex
-n = 0
-n < 0
-r = 0
-r < 0
除数 = 0
减法结果 < 0
除法结果 >= 1
运算符数量 > 3
题目数量过大
题目无法保持唯一
```

### 改进二：设计阶段提前确定核心数据结构

本项目在表达式树设计上花费了一定时间。

以后遇到类似项目，应优先确定：

```tex
核心数据结构
↓
核心算法
↓
模块职责
↓
接口
↓
具体实现
```

避免先写代码后不断修改数据结构。

### 改进三：测试用例与编码同步进行

下一次项目中，可以在完成一个模块的设计后立即编写对应测试。

例如：

```tex
Fraction 设计
    ↓
FractionTest
    ↓
Fraction 实现
```

而不是：

```tex
全部编码完成
    ↓
最后统一测试
```

这样可以更早发现问题。

### 改进四：提前记录实际开发时间

PSP 的价值不仅在于填写最终数字，更重要的是记录过程。

下一次开发时应尽量在每个任务结束后立即记录：

```tex
开始时间
结束时间
实际耗时
遇到的问题
解决方法
```

这样最终的 Postmortem 会更加准确。

